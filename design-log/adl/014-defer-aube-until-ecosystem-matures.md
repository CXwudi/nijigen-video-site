ADL-014: Defer aube Until Ecosystem Integration Matures

Recorded on 2026-09-26. Decision: retain pnpm and stop the aube migration.

The frontend is early enough to change package managers. Aube was evaluated for faster dependency installation, automatic installation before scripts, integration with mise, and everyday developer experience. The intended migration used native `aube-workspace.yaml` and `aube-lock.yaml`, rather than retaining pnpm filenames for compatibility. The evaluated versions were aube 2.4.0, pnpm 12.6.0, and shadcn 4.21.0.

The trial demonstrated that aube can run this frontend. Frozen installation, type checking, lint, formatting checks, all 36 tests, production builds, and a local development-server HTTP check passed on the host. The adapted Docker dependency image also built successfully, and non-root Compose runs passed frozen installation, type checking, and tests. These results establish application compatibility for the exercised paths. They do not establish a project-specific speed advantage; no controlled comparison was completed.

The reason to defer adoption is the amount of integration work required around the package manager:

- Renovate's npm manager does not maintain a native aube lockfile. It could update `package.json` without updating `aube-lock.yaml`, breaking frozen installs. Continuing the migration would require suspending frontend dependency automation or maintaining a separate lockfile-update workflow. The trial selected suspension, but that loss of automation is part of the adoption cost.
- The project's shadcn CLI does not recognize aube in its bundled package-manager detection and falls back to npm. Launching the generator through aube alone does not ensure that its nested dependency-install command uses aube. A scoped shell-activation wrapper was demonstrated, but would require a special entrypoint for adding components. This workaround was not adopted.
- VS Code's built-in npm extension has no aube option in its package-manager or script-runner settings, and its lockfile-preference detection does not recognize the native aube files. Installation metadata can provide additional detection paths, so this is a lack of first-class configuration and native-lockfile integration, not a claim that aube cannot run in VS Code's terminal. No live VS Code workflow was validated in the trial.
- The existing dependency policy does not transfer exactly. Aube 2.4.0 allows versions whose registry metadata omits a publish time, even with `minimumReleaseAgeStrict` enabled; the project's pnpm configuration rejects that case. Also, `strictDepBuilds` must use a supported configuration source such as `.config/aube/config.toml` in this version; copying the setting into workspace YAML does not enforce it. Configuration lookup output alone was insufficient evidence that a policy was enforced.

Docker integration was feasible, but added work: replacing the pnpm base image, installing aube, relocating writable cache and tool state, and validating root-built dependency volumes with a non-root runtime user. The trial chose to disable aube's global virtual store inside containers while retaining its host default. A future second application in the same frontend workspace already shares the workspace-local virtual store; application count alone does not justify a global store. Sharing across independent worktrees would also require deliberate Docker-volume sharing. These are integration considerations, not evidence that aube cannot work with Docker.

For this project, "too young" means the surrounding development tools have not caught up with aube's native workflow. The accumulated exceptions would make routine dependency updates, component generation, and editor actions less predictable. Speed claims and a pleasant standalone CLI do not currently outweigh that maintenance cost. Pnpm 12 already provides automatic dependency checks before scripts and works with the existing mise, Renovate, editor, and Compose workflows.

An alternative is to retain `pnpm-workspace.yaml` and `pnpm-lock.yaml` while running aube. Aube supports this compatibility mode, which would preserve the pnpm file signals used by surrounding tools. However, recognizing pnpm files generally makes those tools invoke pnpm; it does not make them select aube. Local commands, component generators, editor actions, and dependency automation could therefore use different installers against the same project. The installers have separate stores and install state, and the last installation controls the project's dependency links. Compatible lockfile syntax does not establish identical resolution, build-approval, or installation behavior.

This compatibility mode was not validated in the trial and is not assumed to be inherently unstable. It could be viable with explicit ownership of lockfile updates and installation, plus compatibility checks; routing commands through shims would also need to cover each relevant environment. It is deferred here because that coordination adds maintenance work without a measured project-specific benefit over using pnpm consistently. The decision is about predictability and validation cost, rather than a claim that every aube/pnpm combination fails.

Keep the existing pnpm configuration, lockfile, dependency versions, Renovate rules, and the shared Compose approach from [ADL-013](013-shared-development-compose-project.md). Revert the migration implementation and retain this record. This decision defers adoption rather than ruling aube out permanently.

Reconsider when Renovate can maintain native aube lockfiles, shadcn can select aube without a project-specific wrapper, and VS Code's common package-manager actions have a reliable supported path. Verify that the required dependency policies are expressible and effective, and that container installation works with the existing non-root volume lifecycle. Then compare cold installs, cached installs, actual development commands, and CI end-to-end time on this repository under equivalent dependency and security policies.
